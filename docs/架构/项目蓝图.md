## 一、这个项目在做什么

**一句话**：客户把 RSS/Atom/JSON Feed 的网址交给我们，我们替他们盯着；**内容变了就主动推送**，并精确告诉他**哪个字段、从什么变成什么**。

### 核心差异化（竞品做不到的那部分）

| 能力 | 竞品现状 | 我们 |
|---|---|---|
| 检测**新增**条目 | 普遍支持 | 支持 |
| **检测已有条目被修改** | ❌ 多数做不到 | ✅ 核心能力 |
| **字段级 diff** | 少数支持，但不知变的是哪个字段 | ✅ 明确告诉客户 `title: "A" → "A (corrected)"` |
| **原生 webhook 推送** | 有的只输出、让客户轮询 | ✅ HMAC 签名 + 重试 |

**为什么这个差异值钱**：新闻更正错字、竞品悄悄改价格、政策悄悄换附件——**这些都不产生"新条目"**，所以竞品保持沉默。而这恰恰是客户最需要知道的。

### 五个真实使用场景（已验证有人付费在做）

1. **安全告警**——盯 NVD 新增 CVE，而不是等季度审计才发现
2. **竞品监控**——对手改定价，比他还先知道
3. **价格与库存变动**——直接和钱挂钩
4. **政策与合规追踪**——错过截止日期代价极高
5. **技术发布监控**——GitHub release / changelog

**共同点：全都是"忘了看就会出事"的场景。** 这是付费意愿的真正来源，不是"省了几秒钟"。

## 二、系统架构

```
┌─────────────────────────────────────────────────────────────┐
│海外 Vultr（东京）· Ubuntu 24.04 · $6/月                       │
│                                                             │
│  ┌────────────┐                                              │
│  │   Nginx    │ 443/80 · 终止 TLS · ACME 挑战放行            │
│  └─────┬──────┘                                              │
│        │ 反代 + WebSocket 升级                                │
│  ┌─────▼──────────────────────────────────────────┐          │
│  │ Node 服务（systemd 常驻，绑 127.0.0.1:3001）  │          │
│  │                                                  │          │
│  │  src/server.js    HTTP 入口（REST + MCP）        │          │
│  │  src/service.js   调度 · 抓取 · 比对 · 推送       │          │
│  │  src/parser/      三协议解析（RSS/Atom/JSON Feed）│          │
│  │  src/diff/        ★ 哈希粗筛 + 字段级 diff      │          │
│  │  src/notify/      HMAC 签名 webhook + 重试       │          │
│  │  src/security/    SSRF 防护 + DNS 钉 IP          │          │
│  │  src/mcp/         MCP Streamable HTTP（3 工具）  │          │
│  └──────────────────────────────────────────────────┘          │
│        │                                                       │
│  ┌─────▼──────┐   ┌──────────────┐                            │
│  │ 客户端      │   │ 定时调度      │ 每周检查 + 到期降级        │
│  │ HTTP / MCP │   │ (systemd timer)│                           │
│  └────────────┘   └──────────────┘                            │
└─────────────────────────────────────────────────────────────┘
        │ 抓取（服务器出网到境外源）
        ▼
   GitHub Releases · 国外新闻站 RSS · 政府公告页 · 任意公网 Feed

┌─────────────────────────────────────────────────────────────┐
│  客户侧                                                       │
│  · 我们的订阅页面（自建）→ 发 Payoneer 收款链接                │
│  · 客户的 webhook 接收端（他们自己部署）                       │
└─────────────────────────────────────────────────────────────┘
```

### 五个架构决策（及理由）

| # | 决策 | 理由 |
|---|---|---|
| 1 | **Node 只绑 127.0.0.1** | 若绑 0.0.0.0 会暴露端口，**绕过 Nginx 的 TLS 与访问日志** |
| 2 | **Nginx 反代而非直出** | TLS 终止、SNI 多域名共存、访问日志、限流都在这一层 |
| 3 | **MCP 与 REST 共用同一核心逻辑** | 同一功能两个入口，**维护成本几乎不增加**，但多一个分发渠道 |
| 4 | **内存存储（MVP）** | 重启即丢，**验证期可接受**；正式版换 SQLite/Postgres |
| 5 | **境外 VPS 而非国内机+代理** | 抓境外源是产品核心价值，**代理方案会让价值归零**，且架构更简单 |

### 代码规模

```
2143 行 / 7 模块 · Node 22 ESM + fast-xml-parser · 零框架依赖
87 项离线测试全绿，全部经「回退法证伪」（改回旧写法会变红）
```

## 四、阶段性路线与主体需求

### 三个阶段

| 阶段 | 时长 | 月收入 | 服务器 | 收款 | 主体 |
|---|---|---|---|---|---|
| **① 验证期** | 8 周 | 0–$5k | Vultr $5 | **Payoneer 收款链接**（个人）| ❌ **不需要** |
| **② 成长期** | 验证通过后 | $5k–5万 | 升级 $20 | **Payoneer / Airwallex** | ✅ 需要（Airwallex 需企业）|
| **③ 规模化** | $5万+ | $5万+ | 升配 | **Stripe HK** 或 **Checkout 2.0** | ✅ 需要（境外主体）|

### 主体需求的确切触发点

```
验证期（0–5 付费用户）     → ❌ 不需要主体（用收款链接）
     ↓
有付费用户，产品被验证      → ✅ 咨询税务师（第 3 周就该做，别拖）
     ↓
确定要接 Checkout 2.0 或 Stripe
（Checkout 官方要求：香港实体 + 月流水 > $20,000）
                            → ✅ 注册香港公司
     ↓
公司证书 + 银行账户齐备      → ✅ 开 Stripe HK / 申请 Checkout 2.0
```

⚠️ **注意**：如果收入规模不大，**Payoneer 收款链接可以一直用下去**，不必换。
升级的理由只有一个：**人工维护订阅的成本超过了自动化成本**（或需要 Connect 分账）。

### 为什么香港是最优主体选择

| 项 | 香港 | 美国 LLC |
|---|---|---|
| Stripe 费率 | 3.4% + HK$2.35 | **2.9% + $0.30**（更低）|
| 董事要求 | **大陆居民可任唯一董事** | 无限制 |
| 税务编号 | 无（报税制） | **需 EIN**（海外申请慢）|
| 合规负担 | 中（报税+年检+审计报告）| **重**（IRS Form 5472 漏报罚款可达 $25,000）|
| 踩坑代价 | 可控 | **高** |

**结论**：费率虽然高一点，但 **Form 5472 的坑不值得踩**。除非明确做北美市场且有专业会计支持。

### 分层判断标准

| 层 | 回答什么问题 | 判断标准 | 变更频率 |
|---|---|---|---|
| **架构** | 整个项目长什么样 | 涉及多个子系统 | 很少（季度级）|
| **需求** | 做什么功能、验收标准 | 涉及"功能" | 中（月级）|
| **运营手册** | 怎么一步步做 | 涉及"操作步骤" | 高（跟着平台变化）|
| **决策** | 为什么这么选、为什么排除别的 | 涉及"取舍" | 低（决策后很少变）|
| **复盘** | 踩过什么坑、教训是什么 | 涉及"已发生的事" | 追加式 |

**⚠️ 常见错误**：把"为什么选 A 不选 B"写进运营手册。**决策会变（平台被收购、改费率），手册不会自动更新**——一份三个月前正确的手册，今天可能把人导向一个用不了的平台。
