## 一、为什么需要境外服务器

**核心原因：服务器必须能抓取境外 RSS 源。**

| 源类型             | 国内服务器（215.156） | 境外服务器     |
| --------------- | -------------- | --------- |
| GitHub Releases | ❌ 超时           | ✅         |
| 国外新闻站 RSS       | ❌ 超时           | ✅         |
| 政府公告页           | ✅              | ✅         |
| 国内 RSS 源        | ✅              | ✅（绕一圈但可通） |

**这不是技术偏好，是产品核心价值。** 抓不到境外源，客户买这个服务毫无意义。

**实测记录**（2026-10-12）：国内 47.116.215.156 抓取境外源全部超时，  
代码层面已实现代理支持，但**依赖代理可用性 + 需在代理侧配出站网段拦截**（B6 一票否决项）。  
迁境外 VPS 可彻底消除这个风险 —— **这正是选方案乙而非方案甲的原因。**

### 3.7 Step 7 · 配置云防火墙（**5 分钟，强烈建议**）

Vultr 有**两层防火墙**，很多人只配了一层，导致：

- 只配了 ufw → 外网依然可以直接连 22/80/443
- 只配了控制台 → 后续加端口时容易把自己关在门外

### 7-1 建防火墙组

1. `https://my.vultr.com/settings/#firewall` → 右上角 **`+` Add Firewall Group**
2. 命名为 `feedwatch-prod`
3. 点 **Add**

### 7-2 加规则（**按顺序加，最后才设默认拒绝**）

点击刚建的组 → `Firewall Rules` → 添加：

| # | 动作        | 协议  | 端口    | 来源                       | 说明                                                 |
| - | --------- | --- | ----- | ------------------------ | -------------------------------------------------- |
| 1 | **Allow** | TCP | `22`  | 我的 IP（可选）                | SSH。**限制来源更安全**，但国内 IP 动态时可能连不上 → 验证期先放 `Anywhere` |
| 2 | **Allow** | TCP | `80`  | **Anywhere (0.0.0.0/0)** | HTTP，**certbot 签证书必需**，不能限制来源                      |
| 3 | **Allow** | TCP | `443` | **Anywhere (0.0.0.0/0)** | HTTPS，对外服务                                         |
| 4 | **Drop**  | —   | —     | Anywhere                 | **默认拒绝，放在最后加**                                     |

> ⚠️ **顺序很重要**：Drop 规则在列表里靠后，先匹配先生效。  
> 一定要**先加完 Allow 再加 Drop**，否则加完 Drop 后新加的 Allow 会被前面的 Drop 吃掉。

免费额度：**最多 50 条规则**，我们用 4 条。

## 四、Linux 部署

### 架构

```
Node → 127.0.0.1:3001（不暴露公网）
Nginx → 反代 80/443，终止 TLS
systemd → 常驻 + 崩溃自动重启
certbot → 证书自动签发与续期（自带 timer）
```

**对比 Windows 方案的简化**：

| 项    | Windows + IIS                  | Linux + Nginx       |
| ---- | ------------------------------ | ------------------- |
| 反向代理 | ARR + URL Rewrite + web.config | **一个配置文件**          |
| 常驻进程 | 计划任务 + watchdog 脚本             | **systemd（自带崩溃重启）** |
| 证书续期 | ACME node 脚本 + 计划任务            | **certbot 一条命令**    |
| 依赖安装 | 手动装 node + 依赖                  | `apt install` 一条命令  |

### 一键部署

```bash
# 1. 上传代码
scp -r src package.json package-lock.json scripts deploy root@<IP>:/tmp/feedwatch/

# 2. 在服务器上执行
ssh root@<IP>
sudo mkdir -p /opt/feedwatch
sudo cp -r /tmp/feedwatch/* /opt/feedwatch/

# 3. 生成密钥并部署（脚本自动完成 7 步）
export FEEDWATCH_BOOTSTRAP_KEY="$(openssl rand -base64 32)"
sudo -E bash /opt/feedwatch/deploy/deploy-linux.sh \
  --domain api.tiici.com \
  --email bruceonline@163.com
```

> ⚠️ **脚本要求代码已在 `/opt/feedwatch/src`**（第 3 步会检查，不存在就退出）。  
> **所以第1、2 步的 scp 不能省。**

### 脚本做的 7 步

| # | 步骤                 | 关键点                                                             |
| - | ------------------ | --------------------------------------------------------------- |
| 1 | 安装系统依赖             | Node 22 + Nginx + certbot + ufw                                 |
| 2 | 创建系统用户 `feedwatch` | 非 root 运行，`nologin`                                             |
| 3 | 部署应用代码             | `npm ci --omit=dev`                                             |
| 4 | 写密钥文件              | `/etc/feedwatch/env`（权限 **600**），**不接受命令行传参**（会进 shell history） |
| 5 | 配置 systemd         | `Restart=always` + 崩溃退避 + 安全加固                                  |
| 6 | 配置 Nginx           | **先 `nginx -t` 再 reload**；含 MCP WebSocket 支持 + 300s 长连接         |
| 7 | 配置防火墙              | 只放行 22/80/443                                                   |

> ⚠️ **脚本配置的是 ufw（系统层）**。Vultr 控制台的云防火墙是另一层，  
> **两者都要开**，已在 3.7 处理。

### ⚠️ 部署后必须手动做的两件事

```bash
# 1. 申请证书（需DNS 已指向本机）
sudo certbot --nginx -d api.tiici.com --agree-tos -m bruceonline@163.com
# certbot 自带 systemd timer（certbot.timer），证书自动续期，无需额外配置

# 2. 回读确认防火墙两层都在位
sudo ufw status verbose
```

### 对外落地页（已上线）

**访问地址**：https://api.tiici.com/ （根路径即落地页）

| 项 | 值 |
|---|---|
| 源文件 | `web/index.html`（27 KB，单文件，零外部资源）|
| 服务器路径 | `/var/www/feedwatch/index.html`（owner `www-data`，权限 644）|
| Nginx 配置 | `deploy/nginx-site.conf` |
| 部署脚本 | `bash deploy/deploy-web.sh`（可重复执行，含备份与语法检查）|

> ⚠️ **Nginx 必须用 exact match 挂静态页**：
> ```nginx
> location = / { root /var/www/feedwatch; try_files /index.html =404; }
> location = /index.html { root /var/www/feedwatch; }
> ```
> **绝不能用 `location /`** —— 那会把 `/health`、`/v1/monitors`、`/mcp` 全部吞掉，
> 造成「页面能开但 API 全挂」的假象。

验证方式（部署脚本第4 步会自动跑）：
```bash

```

## 六、回滚方案

### 触发条件

- 部署后 30 分钟内验证不通过
- 抓取境外源仍失败
- 出现异常流量或安全问题

### 回滚步骤

```bash
# 1. 停服务（可选，不影响国内站点）
sudo systemctl stop feedwatch

# 2. DNS 改回旧 IP
#    api.tiici.com → 47.116.215.156
```

**回滚窗口内国内 6 个站点零影响** —— 它们不经过新服务器。

### 为什么回滚是干净的

- Node 只监听 127.0.0.1，公网无法直接访问
- TLS 由 Nginx 终止，回滚后旧 IIS 立即接管
- **DNS 生效是唯一需要等待的环节**（TTL 调低后通常 **5–10 分钟**）

### ⚠️ Vultr 特有的坑

| 坑                 | 说明                                                                 |
| ----------------- | ------------------------------------------------------------------ |
| **销毁实例会换IP**      | Destroy 后重建会得到**新的公网 IP**。回滚期间**绝对不要销毁**，保留着才能随时再切回去               |
| **回滚不销毁，只是停计费不了** | 实例开着就一直计费。**回滚决策期间的钱可以承受，但超过1 个月就要 Destroy**（此时 DNS 已在旧服务器，安全上无风险） |
| **要换IP 而不销毁**     | 用控制台的 **Reserved IP**（绑在运行实例上免费），比销毁重建干净                           |

## 七、部署环节常见问题

| 现象              | 原因                 | 处理                                |
| --------------- | ------------------ | --------------------------------- |
| certbot 失败      | DNS 未生效或 80 未通     | 先确认 DNS 已指向新 IP，且云防火墙放行 80        |
