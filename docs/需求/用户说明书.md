## 这是什么（一句话）

**它替你盯着一个网页或订阅源，内容变了就推给你——不用你记得去看。**

---

## 先看一个具体场景

**你是安全工程师。**

某天早上你打开电脑，发现昨晚凌晨 2 点有人公布了一个影响你们所用库的 CVE 漏洞。你们的运维流程是"每周一次例行检查漏洞库"——**这一周里，这个漏洞是敞开的。**

现在你给 NVD 漏洞库配了一个监控：

```
监控点：https://nvd.nist.gov/feeds/xml/cve/misc/nvd-rss.xml
关键词：CVE-2026
频率：每小时
通道：企业微信 / Slack / 邮件
```

凌晨 2 点 07 分，你的手机响了：

```json
{
  "monitor": "nvd-cve",
  "change_type": "added",
  "item_id": "CVE-2026-31415",
  "field": "title",
  "title": "CVE-2026-31415 严重漏洞影响某库 RCE",
  "link": "https://nvd.nist.gov/vuln/detail/CVE-2026-31415",
  "detected_at": "2026-10-12T02:07:11+08:00"
}
```

**这就是这个服务存在的全部理由：把"每周才发现"变成"7 分钟后发现"。**

---

## 它解决的真实问题

| 你现在的做法 | 问题 |
|---|---|
| 手动每天打开官网看一眼 | 忘一次就漏一个月 |
| 每周例行检查 | **窗口期太长，出事时已经晚了** |
| 用 RSS 阅读器订阅 | **阅读器要你主动去看**——它不主动通知你 |
| 写个脚本自己抓 | 抓取挂了没人知道；改版了直接静默失效 |

**核心区别：RSS 阅读器是"你去看它变没变"，这个服务是"变了它来找你"。**

**它们全都是"忘了看就会出事"的场景。**

## 怎么用（三步）

### 第一步：创建一个监控

```
POST https://api.你的域名/v1/monitors
```

```json
{
  "url": "https://example.com/feed.xml",
  "interval": 3600,
  "keywords": ["urgent", "breaking"],
  "extract": {
    "mode": "regex",
    "fields": {
      "title": "<title>(.*?)</title>"
    }
  },
  "deliveries": [
    { "type": "webhook", "url": "https://你的系统/webhook", "secret": "..." },
    { "type": "email", "to": "alerts@你的公司.com" }
  ]
}
```

响应：
```json
{
  "id": "mon_a1b2c3",
  "url": "https://example.com/feed.xml",
  "interval": 3600,
  "status": "active",
  "next_check_at": "2026-10-12T14:00:00+08:00",
  "created_at": "2026-10-12T13:50:00+08:00"
}
```

### 第二步：配置你的接收端

Webhook 推送会带 **HMAC 签名**，请务必验证：

```
X-Webhook-Signature: sha256=...
```

验证方式：用你的 secret 对**原始请求体**算 HMAC-SHA256，比对签名值。**不要跳过这一步**——不验签意味着任何人都能伪造推送。

### 第三步：等着收

就这样。不需要写代码去查。

## 你会收到什么（两种变更，四种类型）

### 变更类型一：新增条目

```json
{
  "change_type": "added",
  "item_id": "唯一标识",
  "title": "条目标题",
  "link": "https://原文链接",
  "published_at": "2026-10-12T02:00:00Z",
  "detected_at": "2026-10-12T02:07:11+08:00"
}
```

### 变更类型二：已有条目被修改（★这是我们的核心能力）

```json
{
  "change_type": "modified",
  "item_id": "同一份条目标识",
  "diff": [
    {
      "field": "title",
      "old": "某公司发布 2024 年报",
      "new": "某公司发布 2024 年报（已更正）"
    },
    {
      "field": "content",
      "changed": true,
      "old_hash": "a3f5...",
      "new_hash": "8c2d..."
    }
  ],
  "detected_at": "2026-10-12T02:07:11+08:00"
}
```

**为什么这条比"新增"更重要**：

新闻网站改一个错字、竞品悄悄调整一个价格、政策文件更新一个附件——**这些都不产生"新增条目"，只产生"已有条目的变化"。**

如果你的监控工具只报新增，这三类变化你**永远看不到**。

## 支持哪些数据源

| 类型 | 说明 |
|---|---|
| **RSS 2.0** | 最常见，绝大多数新闻站和博客都支持 |
| **Atom** | Google 系、部分博客 |
| **JSON Feed** | 新兴格式，兼容性要求高时选它 |
| **普通网页** | 没有订阅源的页面也能监控（提取区域可指定） |

> 提示：很多网站在 `/feed`、`/rss`、`/atom.xml` 或页脚有"订阅"图标，试一下通常能找到 RSS 地址。**有 RSS 优先用 RSS**，更稳定、更省资源。

## 用之前必须知道的三件事

### ① 不保证绝对实时，但有明确延迟

最低 15 分钟一档。如果你的场景要求秒级响应，这个服务不适合。

### ② 对方源没有访问权时，监控会失败

监控公开 RSS 和网页没问题。如果你监控的是需要登录的内部系统，需要额外配置（企业版功能）。

### ③ 免费层有每日限额

超出限额会返回 429。**这是为了防止无限量套餐被滥用**——我们不做"$X/月无限量"那种模式。

## 你可以自己验证它有多准

**这是我们建议你做的第一件事，别急着付费。**

1. 挑一个你真的需要盯的源（推荐：某个安全公告页）
2. 配一个 15 分钟或 1 小时频率的监控
3. 用一周
4. 看两个数字：**有没有漏报**（该报的没报）· **有没有噪音**（不该报的报了）

**这两个数字决定了这个服务对你有没有价值。** 如果噪音太多，用关键词过滤收窄；如果漏报，立刻联系我们。

## 常见问题

**Q：支持 JSON Feed 吗？**
A：支持。RSS 2.0、Atom、JSON Feed 都能解析。

**Q：会因为我抓太频繁被封吗？**
A：默认频率是保守的（24 小时起）。我们尊重源的服务器设置，建议不要超过 15 分钟一档。优先用 RSS 而不是直接抓网页。

**Q：webhook 收不到怎么办？**
A：推送失败会自动重试 3 次。仍失败会发邮件告警，并可在控制台查看投递日志。

**Q：能同时推多个地方吗？**
A：可以。一个监控点配多个通道（webhook + 邮件 + Slack 都可以）。

**Q：数据保存在哪，能导出吗？**
A：变更历史保存 30 天，随时可通过 API 导出为你自己的数据。
