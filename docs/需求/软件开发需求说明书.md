## 📌 收费与主体约束（2026-10-15 追加，影响功能设计）

**这一节记录的不是功能，而是「功能背后为什么这样设计」。** 详细决策见项目目录 `docs/决策记录-收款与主体.md`。

### 当前收款方案

> ⛔ **2026-10-15 v2 纠正**：原文写「验证期用 Payoneer Checkout（个人可开通）」**是错的**。  
> Payoneer 官方条款明确：Checkout 服务**仅面向美国与中国香港实体，不面向中国大陆境内的个人或实体**，  
> 且需**月网店流水 > USD $20,000**、须**已设立或愿意设立香港实体**。  
> 来源：`https://www.payoneer.com/checkout/`（2026-10-15 核实）
>
> **正确方案**：验证期用 **Payoneer 收款链接（Payment Link）** —— 个人可开、无需主体。  
> 操作手册见 `docs/运营手册/Payoneer收款链接操作手册.md`  
> 决策依据见 `docs/决策/决策记录-收款与主体.md` v2

**验证期用 Payoneer 收款链接（个人可开通，无需公司主体）。**

⚠️ **不是 Stripe，也不是 Lemon Squeezy，也不是 Payoneer Checkout。**

- Lemon Squeezy **已于 2024-07 被 Stripe 收购**，且大陆主体不在其卖家支持名单内 → 已排除
- Stripe **明确不支持中国大陆主体** → 需先注册境外公司
- Payoneer **Checkout 2.0** 底层由 Stripe 提供，**仅对美/港实体开放** → 规模化阶段才考虑

### 这对功能设计意味着什么

| 约束                    | 对功能的影响                           |
| --------------------- | -------------------------------- |
| **收款链接无支付成功 webhook** | **订阅状态只能人工维护** —— MVP 阶段不要指望自动开通 |
| **收款链接无自动续费**         | 到期需人工发新链接，**不能承诺"自动续订"**         |
| **无 Tax 自动化**         | 发票只能由平台出（无法自主开发票抬头）              |
| **无 Connect**         | **不能做平台分账**，将来若要分账必须换平台          |
| 支付页面由平台提供             | **订阅界面完全是我们自己的** —— 平台只提供付款跳转页   |

### 因此 MVP 的订阅逻辑：**人工为主**

| 功能                 | 优先级          | 说明                           |
| ------------------ | ------------ | ---------------------------- |
| 套餐状态**表格**         | 🔴 **必须**    | `客户 / 档位 / 到期日 / 状态`，人工维护    |
| `POST /v1/apikeys` | 🔴 必须        | 创建 API Key（**服务端不保存任何支付信息**） |
| 支付确认后**人工开通**      | 🔴 必须        | 确认到账 → 发 Key → 放宽限流          |
| 到期降级               | 🟡 可延后       | 5 个用户以内靠人工记                  |
| 自动扣款               | ❌ **MVP 不做** | 收款链接不支持                      |

### ⚠️ 设计约束（按修正后的情况）

1. **不要在产品里承诺「自动续费」** —— 收款链接做不到，承诺了就是欺骗客户
2. **定价页要写清「付款后 1 小时内开通」** —— 信用卡到账约1 小时，电汇 1–3 天
3. **FAQ 必须说明「客户信用卡账单显示 Payoneer」** —— 否则会被当成诈骗
4. **必须提供 HMAC 验证代码模板**（给客户验签我们的 webhook 推送）  
   不提供的话客户不会验签，我们的服务就是可被伪造的开放端点。

### 主体需求的时间点

**MVP 与验证期（8 周，0–5 付费用户）不需要任何公司主体**（走收款链接）。

注册香港实体的**两个触发条件**：  
① 确定要接 Checkout 2.0 或 Stripe；  
② 月流水接近 Checkout 的 $20,000 门槛。

成本参考：香港主体年维护 ≈$83/月，**是服务器成本（$5）的 16 倍\** —— 验证期收入还没这个数。

3. **需求变更要在文档里记一行**（谁提出、为什么改、什么时间），不要口头改

### 模块 D｜安全 `[竞]`

| ID     | 需求                   | 来源                    | 优先级    | 验收标准                                                    | 状态        |
| ------ | -------------------- | --------------------- | ------ | ------------------------------------------------------- | --------- |
| D1     | **SSRF 防护**（私有网段不可达） | `[竞]` LemWatch 明确列为卖点 | **P0** | 请求 127.0.0.1 / 10.x / 192.168.x / 169.254.x 被拒绝         | ✅ 已实现     |
| D2     | 请求超时与大小限制            | `[推]` 防资源耗尽           | P0     | 超时 10s，响应上限 5MB                                         | ✅ 已实现     |
| D3     | 重定向跟随上限              | `[推]` 防绕过 SSRF        | P1     | 最多跟随 3 跳，每跳重新校验                                         | ✅ 已实现     |
| **D4** | **API Key 签发限流**     | `[用]` 2026-07-16 实测发现 | **P0** | 短窗口 3 把/分钟 + 日配额 20 把，超限返回 429                          | ✅ **已实现** |
| **D5** | **监控点创建限流**          | `[竞]` 防资源耗尽           | P0     | 60s 内最多 10 次                                            | ✅ 已实现     |
| **D6** | **MCP 端点限流**         | `[竞]` 审计修复项           | P0     | 60s 内最多 120 次                                           | ✅ 已实现     |
| **D7** | **API Key 列举与吊销**    | `[推]` 2026-07-16 发现缺口 | **P1** | `GET /v1/apikeys` 列自己的 key；`DELETE /v1/apikeys/{id}` 吊销 | ⏳ **未实现** |

**D1 为什么是 P0**：来源依据 —— LemWatch 官网："Every feed URL is validated against a strict SSRF blocklist so private networks and internal endpoints can't be reached."  
**这是行业公认的必备项，不做等于产品有安全漏洞。**

#### D4 的背景（为什么它曾是 P0）

**2026-07-16 实测发现**：`POST /v1/apikeys` **完全无限流**，20 次调用签发 20 把 Key 全成功（耗时 31ms）。

**危险不在于「多发了几个 Key」，而在于配额是 per-key 的**：

```
总配额 = MAX_MONITORS × Key 数量
```

Key 数无上限 → 内存监控点、定时器、出网流量都能无限放大。  
这是一条**可被外部触发的资源耗尽路径**，所以定为 P0 而非 P2。

**实现要点（易踩坑）**：

| 要点                           | 说明                                                                   |
| ---------------------------- | -------------------------------------------------------------------- |
| 两层限流而非一层                     | 短窗口（3 把/分钟）防脚本刷；日配额（20 把/24h）防跨天累积。**窗口短到拦不住持续累积**                   |
| ⚠️ **清理阈值不能用短窗口**            | 限流桶定期清理的阈值若用 60 秒，日配额桶会在一天内被清空 → **攻击者等过清理周期即可绕过，限流形同虚设**。必须取所有窗口最大值 |
| 429 要带 `retry_after_seconds` | 否则调用方只能反复试错来推断要等多久                                                   |
| 201 要告知 `remaining_today`    | 同上 —— 不告知剩余量，调用方只能靠撞 429 才知道用完了                                      |

**回退证伪**：还原为无限流后，新增的 e2e 用例变红（5 把全放行 201）；  
恢复后放行 3 把、拦截 2 次（`201,201,201,429,429`）。

#### D7 是当前最大的安全缺口（2026-07-16 记录）

**现状：Key 签发后既无法列举，也无法吊销。**

- 签发时明文只显示一次，服务端只存哈希 → 拿不到已有 Key 的列表
- 没有 `DELETE /v1/apikeys/{id}` → **客户 Key 泄露时唯一手段是重启服务**
- 而重启会把**所有客户的 Key 一起作废** —— 一个客户泄露，影响全体

**影响**：验证期只有 0–5 个客户，可接受。**一旦客户数上两位数，这会成为阻塞级问题**  
（运营不敢发 Key，因为无法在不影响别人的前提下吊销某一把）。

**最小实现**：

- `GET /v1/apikeys` → 返回本账号创建的 Key 列表（**只返回 id / label / 创建时间，绝不返回明文**）
- `DELETE /v1/apikeys/{id}` → 吊销；需校验归属（不区分 403/404，对齐现有 `ownedMonitor` 约定）
- 吊销后其创建的监控点如何处置：停掉但保留数据 / 直接级联删除 —— **待定，需与套餐降级逻辑一起设计**
- **引导密钥不可被吊销**（否则会把自己锁死）

**E5 的来源**：某开发者在 RapidAPI 上前 5 个 API 错误格式各不相同，后来统一但要更新全部列表。**第一天就定好。**

#### E7 的教训（值得单独记）

**任何「限制」必须同时做到「强制」与「申报」，只做其中一项等于撒谎。**

2026-07-16 引入免费层配额时，`FREE_INTERVALS` 只用于计算 `/v1/usage` 的申报值，  
**代码从不校验**。实测传 `intervalSeconds:900` 直接 201 建成 ——  
申报 6 小时、实际 15 分钟，`checks_per_day` 偏差 **24 倍**。

**这与被修的 Bug 7（6h 被压成 60s，360 倍超额抓取）完全同型**，只是方向相反。

**回归防护已补**：验证「申报集合 == 实际强制集合」这个恒等式，  
而不是验证某个固定值被拒绝（后者会随配置变更而失效）。

## 一句话总结

> **MVP 只做一条链路：创建监控点 → 检测变化 → 推送通知，砍掉所有不影响"有人付钱"的功能。**
>
> **核心竞争力是「检测已有条目被修改」+「字段级 diff」+「原生推送」，这三点都有竞品官网原文佐证是现有服务的短板。**
>
> **8 周 5 个付费用户是唯一的判定线。达不到就停，不要用"再优化一下"说服自己。**
