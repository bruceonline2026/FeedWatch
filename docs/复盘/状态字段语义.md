# 监控点状态字段语义约定

> 用途：排障时正确解读 `GET /v1/monitors/<id>` 与 MCP `list_monitors` 返回的状态字段。
> 起因：上线前安全审计发现 `status` 字段曾被同时用于两个不同语义，导致
> 「一次网络抖动 = 监控点永久静默失效」。本文档记录修复后的约定。

---

## 一、三个状态字段互不重叠

| 字段 | 语义 | 由谁写入 | 取值 |
|---|---|---|---|
| `status` | **用户的调度意图** —— 用户要不要这个监控点被检查 | 仅 `PATCH /v1/monitors/<id>` | `active` / `paused` |
| `last_check_ok` | **最近一次抓取的健康结果** | 服务端检查流程 | `true` / `false` / `null`(未检查过) |
| `tripped_by_circuit_breaker` | **系统是否已自动熔断** | 服务端调度器 | `true` / `false` |

配套的 `error_count` / `last_error` 是**诊断信息**，不是状态。

**关键约定：健康检查永远不会修改 `status`。**
这正是原缺陷的根源 —— 抓取失败时若把 `status` 写成 `error`，
调度器 tick 的守卫 `if (m.status !== 'active')` 会判定「已停用」并清掉定时器，
于是**一次 DNS 抖动就让监控点永久停止检查**，而 UI 上只显示 `status=error`，
看不出「已停止调度」。

---

## 二、`last_error` 必须结合 `last_check_ok` 解读

`last_error` 有两个写入方，**语义完全不同**，但共用一个字段：

| 场景 | `error_count` | `last_check_ok` | `last_error` |
|---|---|---|---|
| 抓取失败（上游挂了） | ≥1 | `false` | `上游返回 HTTP 500` 等 |
| 抓取成功但 webhook 投递失败 | 0 | `true` | `通知投递异常：...` |
| 全部正常 | 0 | `true` | `null` |

### 因此存在一个「看起来矛盾」的状态

```json
{ "error_count": 0, "last_check_ok": true, "last_error": "通知投递异常：connect ETIMEDOUT" }
```

这不是 bug。**`last_check_ok: true` 已经表明上游是健康的**，
坏的是 webhook 端点。

### 排障时的正确读法

```
读 last_error 之前，先看 last_check_ok：

  last_check_ok === false
      → 上游抓取问题。last_error 里的内容（HTTP 状态码 / DNS / 超时）就是根因。

  last_check_ok === true 且 last_error 以「通知投递异常」开头
      → 上游正常，是 webhook 端点的问题：地址错、证书过期、被拒、端点超时。
        去查 monitor.channels 里的 URL 与 secret，不要怀疑上游 feed。

  last_check_ok === true 且 last_error === null
      → 一切正常。
```

**一句话：`last_check_ok` 回答「上游健不健康」，`last_error` 回答「最后一次出什么问题」。两个要一起看。**

## 三、`tripped_by_circuit_breaker` 的含义与恢复

连续失败达到阈值（默认 10 次）后，服务端会**自动挂起**该监控点：

- `status` → `paused`
- `tripped_by_circuit_breaker` → `true`
- `last_error` → `连续失败 N 次，已自动挂起…`
- 调度器停止，不再重试（避免对已下线的上游无限请求）

### 与用户主动暂停的区别

| 场景 | `status` | `tripped_by_circuit_breaker` |
|---|---|---|
| 用户手动暂停 | `paused` | `false` |
| 系统自动熔断 | `paused` | **`true`** |

前者是人的决定，后者是系统的决定 —— **靠这个字段区分**。

### 恢复方式

上游恢复后，用户显式重新启用：

```
PATCH /v1/monitors/<id>   { "status": "active" }
```

这会同时清零 `error_count` 并解除熔断标记。
（若不清零，调度器会因 `error_count` 仍 ≥ 阈值而立刻再次熔断，导致**永久无法恢复**。）

## 四、给未来改代码的人：新增 `schedule()` 调用点前必须确认

`MonitorService.schedule()` **自身不校验 `monitor.status`**。
若对一个 `paused` 的监控点调用它，会注册一个空转定时器。

**当前生产不可达** —— 已核对 `server.js` 的三处调用点，都保证 `status === 'active'`：

- `POST /v1/monitors` 创建后（默认 `active`）
- `PATCH status=active`（先置 `active` 再排程）
- `PATCH` 仅改间隔时（条件含 `updated.status === 'active'`）

且 tick 守卫生效，空转定时器会在下一轮自清理（最坏存活一个 interval），
**不会误抓、不会泄漏**。

> ⚠️ **将来若新增调用 `schedule()` 的路径，务必先确认 `status === 'active'`。**
> 与 §二 的 `last_error` 一样：现在不改是因为信息已足够、且改响应契约的收益
> 不抵上线前引入回归的代价。等有真实 UI 时再一并处理。

## 五、`resolvedIp` 的判读规则（排障必读）

| 模式 | `resolvedIp` 含义 | 能否用它判断「IP 锁定生效」 |
|---|---|---|
| **直连**（`viaProxy=false`） | = 实际连接的 IP，由我们 `lookup` 钉住 | ✅ 可以 |
| **代理**（`viaProxy=true`） | = 我们指定给代理的 CONNECT/绝对 URI 目标 IP | ✅ 可以 |

**两种模式下该字段都等于「实际连接到的 IP」**（TOCTOU 修复后语义已统一）。
配套的 `viaProxy` 字段用于区分是「我们钉 IP」还是「我们指定代理目标 IP」。

代理模式的 TOCTOU 缺口**已于 2026-10-12 修复**：
`openTunnel` 的 CONNECT 目标与 HTTP 分支的绝对 URI 均改用 `pinnedIp.address`，
`Host` 头与 TLS SNI 仍保留原始域名（虚拟主机与证书校验不受影响）。
**该风险已接受，B6（代理侧出站网段拦截）是唯一防线。**

排障时改看 `safeFetch` 的错误码：

| 错误码 | 含义 |
|---|---|
| `private_address` / `bad_protocol` / `credentials_in_url` | SSRF 防护正常拦截，**预期行为不是 bug** |
| `proxy_error` | 代理拒绝 CONNECT —— 看到这个码即说明**代理路径已被走到** |
| `timeout` | 超时 |
| `dns_failed` | DNS 解析失败 |
