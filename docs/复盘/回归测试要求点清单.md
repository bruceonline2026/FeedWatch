### 交付标准（本清单的用法）

1. **改动前先看 §7 最小回归集**，跑完 6 项再动手。
2. **每次修复类改动，必须做回退证伪**（附录 A 的做法）。只跑通不算验证过。
3. **判断测试是否通过要单独跑**（`npm test; echo $?`），不要用 `a && b; echo $?` —— `&&` 短路会让 `$?` 反映错误的东西。这是项目已犯过的第 9 次失误。
4. **红线**：标 🔴 的 6 项在补上自动化测试前，**任何改动都必须手工验证并在 PR 里贴证据**。

## 一、静默失效家族（最高优先级）

> 这类缺陷的共同特征：**HTTP 200 / 不抛异常 / 测试全绿，但结果是错的。**
> 项目 10 个缺陷中 7 个属于本家族。它们不会被任何「跑一下看看」发现，
> 必须主动构造边界输入去攻击自己的假设。

### R1.1 · PATCH 部分更新不得停调度 🔴 **零覆盖**

| 项 | 内容 |
|---|---|
| **源码位置** | `src/server.js:341-357`（调度决策分支）· `src/service.js:59-79`（`updateMonitor`） |
| **触发变更** | 任何修改 `src/server.js` PATCH 分支、或 `updateMonitor` 的改动 |
| **验证什么** | `PATCH /v1/monitors/:id` 只带 `name` 或只带 `keywords`（**不带 status**）后，`service.timers.size` 必须仍为 1；再带 `intervalSeconds` 才允许重排 |
| **失败意味着** | 用户改个名字就静默停止监控，且 API 返回 200、`GET` 的 `status=active` / `last_check_ok` / `tripped_by_circuit_breaker` **三个字段全都看不出异常** —— 用户以为还在监控，实际早已停摆 |
| **现有覆盖** | ❌ **无**。回退修复后 87/87 全绿 |
| **建议新增** | 在 `scripts/e2e.js` 增加：创建 → `PATCH {name}` → 断言 HTTP 200 **且** `service.timers.size===1`。必须走 HTTP 层（不能直接调 `updateMonitor`，那是复盘里记过的「断言绕过了被测路径」） |

实测证据（附录 A-1）：
```
修复生效:  PATCH(仅改名) HTTP 200 → timers = 1 ✅
回退后:    PATCH(仅改名) HTTP 200 → timers = 0 ❌ 调度已被静默停掉
           GET status=active | last_check_ok=null | tripped=false ← 字段上看不出
```

**⚠️ 实测发现的缺陷（本次新改动的真问题）**：

`FREE_INTERVALS` 默认 `"21600"`（6 小时），落地页也承诺「5 个监控点 · 6 小时检查一次」，
但**代码从不强制它** —— `POST /v1/monitors {intervalSeconds: 900}` 直接返回 201 建成。

```
/v1/usage 申报 → {"monitors":5,"frequency":["6h"],"checks_per_day":20}
创建 intervalSeconds=900 的监控点 → HTTP 201 | 实际 interval = 900 秒
真实 checks_per_day = 480 次/天，申报 20 次/天 → 偏差 24×
```

**这与被修的 Bug 7 是同一类缺陷**：一个常量声称约束 A，实际只作用于 B。
Bug 7 是钳制误作用到续期（超额 360 倍），本次是 `MIN_INTERVAL` 只用于计算申报值、
不参与实际校验（超额 24 倍）。**方向相反，形状相同。**

> 另注：`allowed_intervals` 字段（`src/server.js:414`）返回的是技术允许的 `[900,3600,21600]`，
> 与 `limit.frequency`（配额允许）语义不同，容易被客户端误读。建议后续改名区分。

## 结语：这份清单的局限

1. **我只做了离线验证 + 本地 HTTP 探针。** 真实源测试（`npm run test:live`，28 项）需要出网，
   我未执行 —— 上线前必须在目标服务器跑一次。特别是 `hacker-news / GitHub Releases` 这类
   **境外源必须走代理**，那是唯一能验证 TOCTOU 修复在真实代理上没搞坏的路径。

2. **「测试全绿」不等于「路径被断言过」。** 我这次实测出 4 处覆盖缺口，
   全部符合复盘文档描述的失败模式。这说明：**新增测试时必须做回退证伪**，
   否则很容易写下「看起来测过了」但实际抓不住缺陷的断言。

3. **部署层零覆盖是最薄弱的面。** 那里发生过真实生产事故（10 分钟 500），
   而现在仍然只有人工检查。**建议优先给 `deploy-linux.sh` 加 `systemd-analyze verify`
   和 `nginx -t` 两道自检** —— 这两条能自动抓住本次两处改动各自的核心风险。

4. **文档声称与实测不符的地方，本文已逐条标出**（附录 A-7）。
   建议同步修正 `e2e.js:186` 的文案（IDOR 覆盖范围）与 `regression.js:77` 的测试名
   （重定向那条实际未构造重定向）—— **不准确的测试名比没有测试更危险**，
   它会让下一次审查误以为该面已被覆盖。
