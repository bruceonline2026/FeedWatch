# 提交前自查清单（三个高发模式）

> **为什么有这份清单**：10-12 我们就记录过「静默失效缺陷不会被任何『跑一下看看』的验证发现」。
> 但 10-16 的 4 个新缺陷里仍有 3 个属同一家族 —— **教训没有自动生效**。
> 光把教训写进文档等于没记录，必须变成**动作**。
>
> 这份清单 + `scripts/selfcheck-silent.js` 就是那个动作。

---

## 一、自动检查（提交前必跑）

```bash
npm test                    # 含模式检查，放在最前面
# 或单独跑：
npm run check:patterns      # 12 项模式检查（verbose）
```

**模式不过，功能测试不会执行** —— 这是刻意的：
跑 92 项断言要 3 分钟，先花 1 秒挡住模式问题更划算。

### 三个模式 ↔ 12 项检查

| 模式 | 检查项 |
|---|---|
| **① 静默停调度** | `service.stop()` 有对应行为测试 · PATCH 区分显式改/部分更新 · 熔断用独立标记 |
| **② 只声明不强制** | frequency 申报与强制同源且可达 ·无 `if(false)` 占位 · `limit.monitors` 真被强制 · 签发限流真生效 · 落地页与代码配额一致 |
| **③ 只覆盖部分方法** | 按 id 操作全有归属校验 · `/check` 子路由有校验 · 测试名声称的覆盖 = 实际断言数 · Key 签发显式查引导密钥身份 |

## 二、人工自查（4 个问题，2 分钟）

脚本只能检查模式，**下面这些要靠脑子**：

```
□ 1. 这次改动动了什么「限流 / 权限 / 调度」？
     → 动了就往下逐条问自己

□ 2. 声明的值和实际强制的值，用的是同一个数据源吗？
     ⚠️ 踩过的坑：FREE_INTERVALS 只用于算申报值、代码不校验 → 偏差 24 倍
     → 判据：grep 申报字段名，看它是否也出现在 if 条件里

□ 3. 如果有 N 个方法走同一个校验，我测了几个？
     ⚠️ 踩过的坑：测试名写「GET/PATCH/DELETE/check 均已校验」，
                实际只断言了 GET —— 不准确的测试名比没有测试更危险
     → 判据：数一数 test 函数里实际写了几个断言

□ 4. API 返回 200 的路径，实际行为我查了吗？
     ⚠️ 踩过的坑：PATCH 仅改名 → 调度被静默停掉，但三个状态字段全看不出
     → 判据：找一条「能观察到真实行为」的断言
             （例：等一个 interval，看 last_checked_at 是否被刷新）
```

## 三、必做：回退证伪

**上面全部通过，也不等于「没漏洞」。**

```bash
# 1. 把修复临时改回错误写法
#    例：把 if (!auth.isBootstrap) { 改成 if (false) {

# 2. 跑测试，看会不会红
npm test

# 3. 恢复修复，确认转绿
```

**判据**：改了之后测试**必须变红**。还是绿的 = 这个修复**没有真正的测试防护**。

> 项目已有 5 次「文档说已验证、实际回退后仍全绿」的记录。
> **不证伪的「已修复」，等于没修。**

## 四、什么时候跑

| 时机 | 必须跑 |
|---|---|
| 改 `src/server.js` / `src/service.js` | ✅ 模式检查 + 回退证伪 |
| 改配额、限流、权限相关 | ✅ 模式检查 + 回退证伪 |
| 改部署脚本 / Nginx 配置 | ✅ 线上验证（见 `docs/运营手册/服务器采购与部署手册.md`）|
| 只改文档 | ❌ 不必 |
| 只改 `web/index.html` | ✅ 检查落地页配额与代码是否一致 |

## 五、这份清单自己的局限

**模式检查只能挡住「已知的三类错误」。** 它挡不住：

| 挡不住 | 怎么办 |
|---|---|
| 新出现的第四类模式 | 靠回退证伪 + 代码审查 |
| 业务逻辑错误（改错了但语法对）| 靠功能测试 |
| 配置/依赖漏洞 | 靠 `npm audit` + Dependabot |
| 运维层问题（Nginx/systemd/防火墙）| **目前零自动化覆盖**，只能人工验证 —— 已发生 1 次生产事故 |

⚠️ **通过 ≠ 安全。** 脚本给的只是「这三类模式没被引入」的弱保证。
